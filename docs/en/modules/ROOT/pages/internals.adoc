= Internals
:description: Peano's planned architecture — modules, parser, interpreter, build-time code generation.

[.lead]
How Peano is designed to work inside. `peano-core` now contains the P1 lexer, parser,
immutable AST, resolver-backed evaluator and API provider; the full design is
`PLAN.md` in {repo-peano}[the repository].

== Modules

[cols="1,1,3",options="header"]
|===
| Artefact | Java module | Role

| `peano-core` | `io.vidocq.peano.core` | Engine — exports nothing; provides `jakarta.el.ExpressionFactory`, evaluates constants and resolver-backed value expressions
| `peano-api` | `io.vidocq.peano.api` | AccessorProvider/AccessorTable contract and SOURCE-retained ELAccessible annotation
| `peano-processor` | `io.vidocq.peano.processor` | Annotation processor generating property tables — implemented, build time only
| `peano-compiler` | `io.vidocq.peano.compiler` | AST to Class-File API classes — planned, P7, build time only
| `peano-tck` | — | Official TCK runner, `-Ptck` profile only
|===

== Pipeline

. A hand-written lexer and recursive-descent parser produce an immutable AST (records and sealed interfaces).
. A tree-walking interpreter evaluates the AST. It is the reference behaviour and the oracle of every differential test.
. At build time, `peano-compiler` turns ASTs known in advance into classes; `peano-processor` generates accessor tables in the application's own packages.

== AOT compatibility

Target: no bytecode generated at run time, no `opens`, no `setAccessible`.
The spec's own `BeanELResolver` is the property-access fallback for accessible exported types.
The interpreter uses `java.lang.reflect.Array` only for runtime-typed array coercion
the `empty` operator and array stream sources (EL 6.0 sections 1.25.7, 1.11 and 2.3.1): allocation, element access
and length, with no member lookup, accessibility changes or `java.desktop` dependency.

== Application-owned accessor tables (P6 foundation implemented)

The reflection guard follows generated and stream resolvers in the factory-supplied
chain, before the API's member fallback. It permits direct map/list/resource-bundle/array
property resolution, while deny mode rejects remaining bean/record/static member access.
Explicit bare-method/function fallback, reflective metadata selection and serialized
function restoration also check the policy.

Selected functional interfaces contribute target-keyed conversion tables through the
same provider service. Generated adapters are ordinary Java classes in the application's
module. They invoke the EL lambda and convert its result through the caller context;
factory conversion instead uses the lambda's captured context and factory result coercion.
No proxy, runtime bytecode generation or reflective method lookup is involved.

The processor generates separate tables for accessible source descendants of selected
roots in the current compilation. Runtime dispatch remains keyed by exact class, so
new overloads, covariant returns and override annotations belong to the concrete table.
Static hiding retains the most-derived signature. Generation waits for unresolved
superclass and interface hierarchies across processing rounds; unresolved selections
receive final diagnostics. No binary subtype scan is performed.

AccessorProvider contributes a collection of AccessorTable instances, each an ELResolver
for one exact runtime class. A Java module provides directive registers the public provider,
even when the provider and model package have no exports or opens.
GeneratedAccessorELResolver loads providers through ServiceLoader and snapshots their
tables in an immutable class-keyed map. Duplicate target registrations fail explicitly.
Tables keep evaluation state in ELContext and must support concurrent use.

The factory's getStreamELResolver hook returns a composite containing the table resolver
followed by the stream resolver. The Jakarta API places this hook after custom application
resolvers and before its built-in resolvers. Custom claims keep precedence; unknown types
and properties fall through. Tables claim resolved nulls through the ordinary API flag.
No reflection or accessibility override performs table calls.

The independent consumer fixture verifies a closed bean and record, direct method calls,
typed writes, read-only metadata, nullable results and custom precedence. A comparison
record exported only to jakarta.el produces the same value/type/read-only results through
its table and the API RecordELResolver. The original API-only bootstrap fixture still
compiles without a Peano API requirement.

The runtime foundation validates the service contract with handwritten tables;
the processor now emits property tables using the same contract.
Generated method metadata is implemented. Exact runtime-class registration intentionally requires separate
tables for subclasses.

== APT property generation (implemented)

ELAccessible or the peano.accessorTypes option selects owned model types.
PeanoAccessorProcessor is discovered on javac's processor module path and generates
one provider per selected type through Filer, with the model as originating element.
Source names include the application module; resource fragments target that
single-module compilation's class output. Generated Java files carry the project license.
Provider names use the binary model name followed by __PeanoAccessors.

Generated tables call public getters and setters directly. Primitive boolean isX
getters take precedence over getX; acronym property names retain their capitals.
Inherited properties and write-only setters are supported; records expose read-only
component accessors. Known null results are claimed, setter operands use ELContext
conversion, and accessor failures preserve ELException or wrap their cause.
Metadata queries do not execute getters.

Unrelated annotations are not claimed. Explicit type names are retried across
processing rounds, allowing another processor to generate a selected model.
Unresolved names are errors when processing finishes. Foreign/unnamed modules,
private enclosing types, ambiguous write-only setters and type-variable bean
properties receive diagnostics. Compile one application module per javac invocation.

The integration fixture runs the compiled consumer without the processor module.
Generated properties are checked against API BeanELResolver on the same API-qualified
exported bean; closed model access cannot rely on that reflective fallback.

== Generated methods and metadata (implemented)

MethodGenerator emits declared erased signatures, direct call branches and static
runtime annotation literal classes for public selected-model methods.
MethodDescriptor protects its parameter/annotation arrays and creates fresh Jakarta
MethodInfo data. Annotation literals implement Java equality/hashCode, including
nested annotations, enums, class constants, arrays, NaN and signed zero.
Array-valued members return fresh arrays. No dynamic annotation proxy is created.

MethodSelection shares overload rules with the API-accessible reflective metadata
fallback. Declared primitive/wrapper descriptors remain distinct; equally matched
unrelated overloads remain ambiguous. Conversion probes use ELContext.
Generated varargs branches allocate typed arrays in Java source; neither reflective
array allocation nor runtime bytecode generation prepares method parameters.

The table resolver binds its immutable catalog in ELContext during ordinary
resolver callbacks, including conversion callbacks that leave resolution unclaimed.
Metadata reads reuse that snapshot; custom contexts can discover it lazily through
the same services. Generated metadata is queried before public-member reflection.
References retain raw evaluated parameters without invoking the referenced method.

Invocations preserve custom resolver precedence. Captured FunctionMapper calls
first consult their declaring owner's generated static table, then retain the
documented API fallback if unresolved. Getter/setter and method exceptions preserve
ELException or wrap the underlying failure as its cause.

Metadata constants must be accessible to the owning application package/module.
Specialized inherited generic parameters are diagnosed. Object-declared methods,
constructors and synthetic stream/optional metadata retain their existing fallback
or pending status; exact-class dispatch still requires separately selected subclasses.
All emitted Java platform names are qualified to survive application names such as Class or Object.

== Lexer (implemented)

The internal `syntax` package tokenizes eval-expression bodies, without their expression delimiters.
Composite text and expression delimiters are handled by `ExpressionParser`.
Tokens are immutable records with the original text and a half-open UTF-16 source span.
String tokens also retain the decoded value; numeric conversion belongs to evaluation.

The lexer follows EL 6.0 sections 1.3, 1.17 and 1.26 for literals, reserved words,
identifier character ranges, whitespace and longest-match operators.
Both quote escapes are accepted with either string delimiter, as permitted by section 1.3.
Illegal characters and malformed strings raise `ELException` with a zero-based source offset.
Each tokenization owns its cursor and returns an immutable list ending in an EOF token.

== Parser and AST (implemented)

`Parser` uses recursive descent to turn expression-body tokens into a sealed AST
of records. Operator precedence and associativity follow EL 6.0 section 1.16.
The grammar includes navigation, function and method calls, assignment, sequences,
lambdas, lists, sets and maps. Parsing these constructs does not yet evaluate them.
All AST collections are copied into immutable lists.

`ExpressionParser` handles literal text, immediate and deferred delimiters, and
composite expressions (section 1.2). It balances collection braces and quoted strings,
rejects nested eval-expressions and mixed immediate/deferred composites, and delegates
bodies to `Parser`. Errors and token spans use offsets in the original expression.

== Constant evaluation and coercions (implemented)

The interpreter evaluates literals, arithmetic, comparison, logic, `empty`,
conditional expressions, string concatenation and constant sequences.
`and`, `or` and `?:` discard the unused branch without evaluating it.
Single eval-expressions retain their value type; composites concatenate string values
before conversion to the expected type.

Numeric operators select `Long`, `Double`, `BigInteger` or `BigDecimal` according
to section 1.7. Decimal equality respects scale, while ordering uses numeric comparison.
Coercions distinguish primitive null defaults from nullable reference targets, and cover
strings, numeric types, booleans, characters, enums and arrays (section 1.25).

`PeanoExpressionFactory` is registered with `provides` in the core module.
Its package is neither exported nor opened. Value expressions apply the expected
type through `ELContext.convertToType`, allowing the context to override conversion.
Operator operand conversions also use the evaluation context.

Java platform conversion uses 46 statically compiled adapters; selected application
interfaces use generated adapters. PropertyEditor conversion remains undecided.
Evaluation listeners and value/method expression serialization are implemented.

== Resolver-backed values (implemented)

The interpreter resolves identifiers in this order: lambda-scope arguments,
captured variables, the context's resolver chain, imported static fields and imported classes.
VariableMapper entries are captured when an expression is created; later mapper changes
do not change its bindings. No VariableMapper is required when the context disables it.

Property reads use `ELResolver.getValue`; a resolved null value remains distinct from
an unresolved name. Null bases and keys short-circuit reads, while terminal lvalue
operations reject null dereferences. Each resolver operation clears the resolution flag
before invocation and checks whether the resolver claimed the property.

ValueExpression getType, isReadOnly and setValue delegate the terminal operation to
the resolver without invoking the terminal getter. Writes convert to the property's
actual writable type through ELContext before setValue for non-root properties.
Root namespace writes pass the original value to the resolver without inferring
a type from a current bean value. This supports reassignment of null or dynamically
typed names and avoids the API BeanNameELResolver null-type defect (API-003).
Root ownership checks use isReadOnly instead of inspecting the current value type.
getValueReference retains the
evaluated base and key. Metadata reports writable types from the resolver rather than
inferring them from current values; read-only static fields have a null writable type.
Resolver runtime failures are wrapped in ELException with their original cause.

The independent Java module fixture verifies maps, a hidden bean through an application
resolver, an API fallback denied by module boundaries, and a record package exported
only to `jakarta.el`. It uses no classpath, opens or access overrides.

Known upstream limitation: jakarta.el 6.0.1 ArrayELResolver rejects boxed values when
writing primitive arrays (API-001 in BUG.md). Object-array writes and primitive-array
reads are supported; Peano preserves custom resolver precedence and does not bypass
resolver failures with a direct array write.

== Functions, methods and assignments (implemented)

FunctionMapper methods are captured at expression creation and must be public/static.
Functions invoke the captured declaring class/name/parameter descriptor through the
API's StaticFieldELResolver; changes to the mapper do not change existing expressions.
Ordinary method calls delegate to the context resolver's invoke operation, including
static imports and constructors. Custom application resolvers keep invocation precedence.
Bare MethodExpression references additionally use the documented API BeanELResolver
or StaticFieldELResolver fallback if the chain does not handle invocation (section 1.6).
Thrown resolver failures remain failures; inline calls receive no extra fallback.

MethodExpression supports bare references, inline parameters, MethodExpression-valued
variables and literal text. Inline arguments override invocation arguments, expected
parameter arrays are copied, and actual return types are checked when requested.
MethodInfo and MethodReference evaluate targets/arguments without invoking the referenced
method; argument expressions themselves may perform evaluation. References include
the base, declared signature, annotations and evaluated argument values.

The temporary MethodMetadata fallback scans public signatures and annotations accessible
to the Jakarta API module, including accessible interface/superclass declarations.
It distinguishes exact primitive/wrapper descriptors and requires a unique most-specific
match among equally scored candidates. It performs no member invocation, access override
or bytecode generation. Generated accessor metadata takes precedence for selected models.
Closed-package custom invocation works without metadata; generated tables supply metadata
and requested return-type validation for selected hidden methods.

Assignments freeze the left-hand base/key before evaluating the right-hand expression,
including variable aliases, then return the original right-hand value. Non-lvalues and
lambda arguments are rejected. Semicolon and string concatenation retain their EL semantics.

The API's inaccessible-method fallback currently produces a wrapped NPE instead of
MethodNotFoundException (API-002). It remains unable to invoke the closed-package method;
the custom resolver path works, and no fallback weakens module boundaries.

== Lambdas and collection construction (implemented)

Lists, sets and maps evaluate their element/key/value expressions left to right and
return fresh mutable collections. Nulls are retained, sets remove duplicate values
using Java equality, and later map entries replace earlier values for equal keys.

Lambda AST nodes create Jakarta LambdaExpression values backed by an interpreter body.
Parameters use the API's ELContext lambda scopes. Free enclosing lambda arguments are
captured at construction, including null values, so closures returned inside collections
retain their lexical environment. Own and nested parameter names are excluded from capture.
Body scopes are restored in finally blocks, including failed evaluations.
The API enforces argument counts and ignores extra arguments according to section 1.20.
No proxy, member reflection, bytecode generation or module access override is added.

Java functional conversion uses ordinary compiled private records implementing
all 43 public java.util.function interfaces plus Runnable, Callable and Comparator.
Adapters invoke the EL lambda, preserve array arguments, and coerce primitive results
through the caller context; closures and scope cleanup remain intact. Factory conversion
uses the lambda's captured context and intrinsic result coercion. Selected application
interfaces use build-time generated adapters. No dynamic proxy or runtime bytecode
generation is introduced.

Expression equality and hash codes use normalized immutable syntax, ignoring
whitespace, operator aliases and the choice of immediate/deferred delimiter.
Operand order, literal text, expected types and captured bindings remain significant.
Original source and positions are retained for diagnostics and getExpressionString.

== Collection pipelines (implemented)

The factory supplies StreamELResolver through the Jakarta API's getStreamELResolver hook.
Application resolvers retain precedence. Collections and both object and primitive
arrays expose stream(). Map collection views can serve as sources too.
Private pipeline and optional records use direct dispatch inside the closed core
module, without reflective member invocation, exports or opens.

Java streams implement lazy filter, map, flatMap, distinct, sorted, peek, limit and
substream pipelines. Terminal operations implement forEach, iterator, toArray,
toList, reduce, min, max, average, sum, count, anyMatch, allMatch, noneMatch and findFirst.
The EL callbacks invoke Jakarta LambdaExpression directly with their evaluation context.
Count traverses elements so peek callbacks are not skipped by Java's sized-source optimisation.
Sources are unaffected by sorting, and toList returns a fresh mutable list.
Pipelines hold single-use Java stream state; obtain another stream from the source
to perform another terminal operation.

EL optional results distinguish absence from a present null element. Empty aggregates
and searches use empty optionals, including all three match operations.
Get on an empty result throws ELException; orElseGet and ifPresent execute their
callbacks only when needed. Arithmetic uses the interpreter's context-aware numeric rules.

These operations are available through value-expression invocation. MethodExpression
metadata and declared return-type checks for synthetic stream/optional operations
remain future work. Selected closed-package application methods now have generated metadata.

== Evaluation events and serialization (implemented)

Text ValueExpression.getValue and MethodExpression.invoke/getMethodReference notify
the supplied context before evaluation and after successful completion, following
the Jakarta API hooks and reference implementation. Failed evaluation or conversion
does not report successful completion. Metadata lookup and value writes do not emit
outer evaluation events. Object-valued variable bindings do not emit synthetic events.
Property notifications stay with ELContext.setPropertyResolved(base, property);
the interpreter adds no duplicate property event. Listeners and their exception
handling are owned by the Jakarta API context.

Value and method expressions serialize through an internal serialization proxy.
It stores the expression source, expected types, captured variable expressions and
public static function descriptors. Restoration parses a fresh AST and rebuilds
the saved bindings; it does not capture the original context or consult the receiving
context's variable/function mappings to replace saved bindings.
Function descriptors restore public method metadata with Class.getMethod, while
invocation remains delegated to Jakarta's resolver and preserves Java module boundaries.
The parser tree and java.lang.reflect.Method objects are not serialized.

Captured object values must themselves support Java serialization, otherwise
ObjectOutputStream reports NotSerializableException. Evaluated streams and arbitrary
lambda objects are not added to the serializable payload contract.
Named-consumer tests round-trip a pipeline, an API-qualified mapped function and
a method bound to a serializable record, with no exports or opens toward the core.
