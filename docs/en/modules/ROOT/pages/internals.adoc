= Internals
:description: Peano's planned architecture — modules, parser, interpreter, build-time code generation.

[.lead]
How Peano is designed to work inside. `peano-core` now contains the P1 lexer, parser,
immutable AST, resolver-backed evaluator and API provider; the full design is
`PLAN.md` in {repo-peano}[the repository].

== Pipeline

. A hand-written lexer and recursive-descent parser produce an immutable AST (records and sealed interfaces).
. A tree-walking interpreter evaluates the AST. It is the reference behaviour and the oracle of every differential test.
. At build time, `peano-compiler` turns ASTs known in advance into classes; `peano-processor` generates accessor tables in the application's own packages.

== AOT compatibility

Target: no bytecode generated at run time, no `opens`, no `setAccessible`.
The spec's own `BeanELResolver` is the property-access fallback for accessible exported types.
The interpreter uses `java.lang.reflect.Array` only for runtime-typed array coercion
and the `empty` operator (EL 6.0 sections 1.25.7 and 1.11): allocation, element access
and length, with no member lookup, accessibility changes or `java.desktop` dependency.

== Lexer (implemented)

The internal `syntax` package tokenizes eval-expression bodies, without their expression delimiters.
Composite text and expression delimiters are handled by `ExpressionParser`.
Tokens are immutable records with the original text and a half-open UTF-16 source span.
String tokens also retain the decoded value; numeric conversion belongs to evaluation.

The lexer follows EL 6.0 sections 1.3, 1.17 and 1.26 for literals, reserved words,
identifier character ranges, whitespace and longest-match operators.
Both quote escapes are accepted with either string delimiter, as permitted by section 1.3.
Illegal characters and malformed strings raise `ELException` with a zero-based source offset.
Each tokenization owns its cursor and returns an immutable list ending in an EOF token.

== Parser and AST (implemented)

`Parser` uses recursive descent to turn expression-body tokens into a sealed AST
of records. Operator precedence and associativity follow EL 6.0 section 1.16.
The grammar includes navigation, function and method calls, assignment, sequences,
lambdas, lists, sets and maps. Parsing these constructs does not yet evaluate them.
All AST collections are copied into immutable lists.

`ExpressionParser` handles literal text, immediate and deferred delimiters, and
composite expressions (section 1.2). It balances collection braces and quoted strings,
rejects nested eval-expressions and mixed immediate/deferred composites, and delegates
bodies to `Parser`. Errors and token spans use offsets in the original expression.

== Constant evaluation and coercions (implemented)

The interpreter evaluates literals, arithmetic, comparison, logic, `empty`,
conditional expressions, string concatenation and constant sequences.
`and`, `or` and `?:` discard the unused branch without evaluating it.
Single eval-expressions retain their value type; composites concatenate string values
before conversion to the expected type.

Numeric operators select `Long`, `Double`, `BigInteger` or `BigDecimal` according
to section 1.7. Decimal equality respects scale, while ordering uses numeric comparison.
Coercions distinguish primitive null defaults from nullable reference targets, and cover
strings, numeric types, booleans, characters, enums and arrays (section 1.25).

`PeanoExpressionFactory` is registered with `provides` in the core module.
Its package is neither exported nor opened. Value expressions apply the expected
type through `ELContext.convertToType`, allowing the context to override conversion.
Operator operand conversions also use the evaluation context.

Remaining work includes method/function execution, assignment operators, lambdas
and collection construction.
Functional-interface adaptation and PropertyEditor conversions are not implemented.
Evaluation listeners and expression serialization remain P5 work.

== Resolver-backed values (implemented)

The interpreter resolves identifiers in this order: lambda-scope arguments,
captured variables, the context's resolver chain, imported static fields and imported classes.
VariableMapper entries are captured when an expression is created; later mapper changes
do not change its bindings. No VariableMapper is required when the context disables it.

Property reads use `ELResolver.getValue`; a resolved null value remains distinct from
an unresolved name. Null bases and keys short-circuit reads, while terminal lvalue
operations reject null dereferences. Each resolver operation clears the resolution flag
before invocation and checks whether the resolver claimed the property.

ValueExpression getType, isReadOnly and setValue delegate the terminal operation to
the resolver without invoking the terminal getter. getValueReference retains the
evaluated base and key. Metadata reports writable types from the resolver rather than
inferring them from current values; read-only static fields have a null writable type.
Resolver runtime failures are wrapped in ELException with their original cause.

The independent Java module fixture verifies maps, a hidden bean through an application
resolver, an API fallback denied by module boundaries, and a record package exported
only to `jakarta.el`. It uses no classpath, opens or access overrides.

Known upstream limitation: jakarta.el 6.0.1 ArrayELResolver rejects boxed values when
writing primitive arrays (API-001 in BUG.md). Object-array writes and primitive-array
reads are supported; Peano preserves custom resolver precedence and does not bypass
resolver failures with a direct array write.
