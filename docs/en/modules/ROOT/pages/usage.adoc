= Usage
:description: Intended usage patterns of Peano — standalone, embedded, build-time accessors. In design.

[.lead]
Constant and resolver-backed value expressions work through `ExpressionFactory.newInstance()`
and `StandardELContext`; see xref:getting-started.adoc[Getting started].
ValueExpression get/set/metadata, variable bindings and imports are implemented.
Functions, method calls, MethodExpression metadata and assignments are implemented.
Lambda construction, list/set/map construction and chapter 2 collection pipelines
are implemented. Java functional-interface adaptation, container integration and
code generation remain planned.

== Standalone evaluation

`ELProcessor` and `ELManager` in a plain Java SE program: define beans, functions and variables, evaluate `${}` expressions, use lambdas and collection operations (`orders.stream().filter(o -> o.paid).map(o -> o.total).sum()`). Milestones P1–P5.

== Embedded by a container

Ibarra (Jakarta Pages 4.0) obtains Peano through `JspApplicationContext.getExpressionFactory()`. Any other component can do the same through `ExpressionFactory.newInstance()` and its own `ELContext`.

== Reflection-free property access

Types selected at build time get an accessor table generated by `peano-processor` (milestone P6). Peano's resolver then reads and writes their properties with direct calls — no reflection, and it works for public types in packages your module does not export. A switch (planned: `peano.reflection=deny`) turns the reflective fallback into an error, to prove in tests that an application runs reflection-free.

== Compiled expressions

Expressions known at build time — Jakarta Pages expressions first — are compiled to classes with the Class-File API (milestone P7). Expressions built from strings at run time are interpreted.
